03 / EXECUTION CONTROL

Blocking gives the CPU to other work.

Step through an empty-buffer read. Data availability and CPU availability are separate events.

Protect the transition

A writer must not sneak between the empty check and waiter registration: that could lose a wakeup (try it in the race laboratory below). Never sleep while retaining the pipe lock.

Wakeup is permission to try again

After resuming, recheck the condition under protection: another reader may already have consumed the data. This is the Mesa-style rule from the monitors session (S09): while (!condition) wait();, not if.

04 / THE SAME PROBLEM IN COURSE TOOLS

A pipe is a bounded buffer you already know.

The producer–consumer (S08) and monitor (S09) sessions solve this exact problem. Here is the one-byte pipe written with each tool. Highlighted lines are the ones that block.

struct pipe {
  char buf[C];
  int  r, w, n;                 /* ⑤ metadata                  */
  pthread_mutex_t lock;         /* ⑤ protects buf, r, w, n     */
  pthread_cond_t  not_empty;    /* ⑥ readers wait here (n == 0) */
  pthread_cond_t  not_full;     /* ⑥ writers wait here (n == C) */
};
void pipe_write(struct pipe *p, char ch) {
  pthread_mutex_lock(&p->lock);
  while (p->n == C)               /* full  */
    pthread_cond_wait(&p->not_full, &p->lock);
  p->buf[p->w] = ch;
  p->w = (p->w + 1) % C;
  p->n++;
  pthread_cond_signal(&p->not_empty);
  pthread_mutex_unlock(&p->lock);
}
char pipe_read(struct pipe *p) {
  pthread_mutex_lock(&p->lock);
  while (p->n == 0)               /* empty */
    pthread_cond_wait(&p->not_empty, &p->lock);
  char ch = p->buf[p->r];
  p->r = (p->r + 1) % C;
  p->n--;
  pthread_cond_signal(&p->not_full);
  pthread_mutex_unlock(&p->lock);
  return ch;
}
Lock = ⑤. Every check and update of n, r, w happens while holding it.
Condition variables = ⑥. pthread_cond_wait enqueues, sleeps and releases the lock as one step. That single step is what prevents the lost wakeup in Section 03.
while, not if. pthread_cond_signal only makes a waiter READY (Mesa style). By the time it runs, the condition may be false again.
semaphore empty = C;   /* free slots   (C − n)     */
semaphore full  = 0;   /* stored bytes (n)         */
semaphore mutex = 1;   /* protects buf, r, w       */
void pipe_write(char ch) {
  wait(empty);       /* blocks while full  */
  wait(mutex);
  buf[w] = ch;
  w = (w + 1) % C;
  signal(mutex);
  signal(full);
}
char pipe_read(void) {
  wait(full);        /* blocks while empty */
  wait(mutex);
  char ch = buf[r];
  r = (r + 1) % C;
  signal(mutex);
  signal(empty);
  return ch;
}
Counts replace n. full tracks stored bytes and empty tracks free slots. wait() is the check and the sleep in one atomic operation, so there is no separate test to protect.
Order matters. Swap to wait(mutex); wait(empty); and a writer facing a full buffer sleeps while holding mutex. The reader can never enter to make space: deadlock.
EOF is awkward. A reader asleep in wait(full) cannot learn that the last writer closed unless the close path posts extra signals. The lock + wait-queue structure of Fig. 1 handles “wake everyone and recheck” more naturally.

Try reading 4 bytes: “CATD” crosses a write boundary. A protocol can add a delimiter or length field when it needs messages. This example has one writer and no interruptions; it returns min(requested, available) while data exists.

A pipe is one-way in this guide. For two-way communication, use two pipes with opposite directions. FIFO means bytes emerge in enqueue order; it does not guarantee fair scheduling among processes.

07 / CONNECTING THE MODEL TO SELFIE

Same buffer mechanics. A new path through mipster.

The left column traces the existing write syscall through the course’s selfie.c. The right column sketches how a pipe write identified by a global pipe ID could follow the same path.

Existing code · selfie.c

How write() travels today

  1. The program calls write(fd, buffer, size), which jumps to a wrapper that emit_write() placed in the binary at compile time.
  2. The wrapper loads a0 = fd, a1 = buffer, a2 = size from the stack, sets a7 = SYSCALL_WRITE (64) and executes ecall.
  3. The trap ends mipster_switch(). mipster() calls handle_exception(), which reaches handle_system_call() and dispatches on a7.
  4. implement_write(context) reads the arguments through get_regs(context) and copies the bytes out of guest memory with copy_buffer(context, vbuffer, IO_buffer, size, 0).
  5. The result goes into a0, and set_pc(context, get_pc(context) + INSTRUCTIONSIZE) moves past the ecall.
Design sketch · not existing code

How a pipe write could travel

  1. Add a syscall number where selfie.c says “you should add new syscalls IDs here”, plus a wrapper such as emit_pipe_write() with a0 = pipe ID, a1 = buffer, a2 = size.
  2. Add a branch to handle_system_call() that calls implement_pipe_write(context).
  3. Look up the ID in a global pipe registry. Invalid ID → a0 = −1, advance the PC.
  4. Space available → copy bytes from guest memory into pipe storage (the same copy_buffer direction as write), update r, w, n, wake a waiting reader, put the byte count in a0, advance the PC.
  5. Buffer full → mark the context BLOCKED, add it to the pipe’s waiting writers, and do not advance the PC.
Not advancing the PC gives you the recheck for free. a0–a2 and a7 still hold the original arguments, so when the context runs again the ecall traps again and implement_pipe_write() examines the buffer from scratch: the Mesa-style while loop, built into the machine. If a call can block after moving only part of its bytes, save that progress (for example, advance a1, shrink a2 and keep a running total in the context), or the retry will send bytes twice.
Blocking needs a scheduler. Today mipster() simply resumes the same context (to_context = from_context, next to the comment “TODO: scheduler should go here”). A blocked context must not be resumed, so this is the place where a scheduler has to choose a different READY context.

Model and references

This is a deterministic teaching model: one writer, one reader, an 8-byte ring, explicit dispatch, and serialized protected operations. Real systems can support multiple readers and writers; locking, wake policies, partial transfers and storage layouts vary. Nonblocking mode, interruption and multiwriter atomicity are outside the simulations.
